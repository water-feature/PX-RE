# B13 v4 — real-library audit and revised candidate

## Outcome

The supplied v3 helper falls back to full parsing on every one of the 927 uploaded manifests. None has a UUID header. The proposed 44.26x reduction therefore does not apply to v3 on this library. Its binary build is reproducible and structurally sound, but its optimization does not activate here.

A revised, conservative v4 helper activates on all 927 manifests and produces the same 17-byte UUID output in every case. It avoids full preload parsing only when the bounded header proves that stock cannot dispatch to its UUID converter. UUID-bearing files always use the stock parser. This is an application ELF candidate, not a flashable update or a hardware-validated result.

## Important stock-parser detail

The stock header mapper initializes every field's token position to **15**, then overwrites positions for recognized headers. It does not use an invalid-column sentinel. When processing a row it dispatches to the first matching field in field order.

Consequently, absence of a UUID header alone does NOT universally imply a zero UUID. If all earlier fields are mapped elsewhere, an extra row token at index 15 can reach the UUID handler implicitly.

V4 proves UUID unreachable by requiring:

1. a complete header within the 511-byte read;
2. no exact UUID header token;
3. at least one of Mono Pitch or Mono Collapse absent from the header.

An absent Mono Pitch (field 9) or Mono Collapse (field 13) keeps its stock position at 15 and intercepts any token at index 15 before UUID (field 14). Therefore later rows cannot modify the UUID. All three uploaded header shapes satisfy this condition.

The cache-entry constructor initializes all 17 UUID bytes to zero at 0x34C6C..0x34C82. GetGroupFileInfo copies those bytes only after successful group and velocity parsing. On failure the startup worker's pre-zeroed output remains zero. The worker ignores the return code and still calls dictionary Insert. A later exact-code audit establishes that Insert skips UUIDs containing any zero byte; therefore these files do not create stored UUID-dictionary entries. V4's zero result therefore preserves the UUID value for these files even when later parsing would fail. It deliberately defers cache creation and its other side effects until runtime.

## V3 review findings

- Rebuilding its assembly object produced identical bytes.
- Rebuilding its candidate produced the supplied SHA-256 exactly: 35c6619daa83fc2a46b2eb006b9c9054d2a9390cd82f972ab621c0478279a716.
- All original structural checks passed; 489 bytes differ from the supplied baseline.
- The original test converter uses high-nibble-first ordering. Stock StrToGUID is low-nibble-first. Expected values were generated by the same wrong stub. The firmware calls the real stock converter, so this is a harness defect rather than a candidate conversion defect.
- V3 selects the first duplicate UUID column. Stock's header mapper selects the last. A synthetic duplicate-column test reproduced the mismatch.
- Stock startup ignores parsing failure but leaves its UUID output zero; V3's UUID fast path could instead publish a nonzero value from a subsequently failing file. V4 avoids this issue by retaining full parsing whenever UUID is explicitly present.

## V4 implementation and ABI

Only the startup call at 0x3527C is redirected. The wrapper keeps the stock eight-integer-argument layout and is intentionally valid only for this audited call site: arguments 4 through 7 are null and argument 8 is the pre-zeroed UUID output. Fallback restores those arguments exactly.

Five callee-saved registers are pushed. Entry RSP modulo 16 is 8; the five pushes make it 0; the 0x220 allocation and two fallback argument pushes preserve alignment at each call. The eighth argument is captured from 24(RSP) after the first push. The 512-byte buffer starts at RSP+0x20; at most 511 bytes are read and the terminating NUL remains inside the allocation. The complete header is tokenized with the stock skip-empty-tab convention. Open/read failures and incomplete headers fall back to stock. No new thread or background cache warmer is introduced.

Text: 0xF9240..0xF93C6, 390 bytes. CFI: 0xFA528..0xFA590, 104 bytes, followed by the zero terminator. The added unwind lookup entry is sorted after the existing 870 entries. The existing RX mapping and ELF file size remain unchanged.

## Validation and its limits

The real-library runner executes the assembled helper with host open/read/close wrappers. For the reference UUID projection it executes extracted stock GetNextLine, AdvanceThroughNextToken and StrToGUID machine code, redirecting their memcpy and stack-guard dependencies. Header mapping, field-order dispatch and first-conversion behavior are modeled directly from the audited GroupFileParse disassembly, including default position 15. It does NOT execute the full QNX parser or velocity parser. This distinction matters: zero UUID equivalence is established; full return-code/cache equivalence is neither claimed nor intended.

| Check | Result |
| --- | --- |
| V3 on real library | 927 stock fallbacks, zero fast successes |
| V4 on real library | 927 fast successes, zero fallbacks |
| V4 UUID projection comparison | All 17 bytes match for all 927 files |
| Host boundary/fallback tests | 18 pass, zero failures |
| V4 structural validator | Pass |

Boundary tests cover CR/CRLF, empty columns, UUID and duplicate UUID fallback, exact token matching, incomplete headers, empty files, open/read failure, zero-length reads, both Mono fields causing conservative fallback, and a newline just inside/outside the 511-byte bound. Fallback stubs check the restored arguments and return code. Guard bytes verify the 17-byte output write.

The four direct stock cache consumers are the startup worker, GroupFileUpdateFolder, CSampleGroup::SwitchSampleGroup and a CMessageAudioLoop::HandleMessage branch. The constructor waits for preload completion and then switches its four slots sequentially. Direct runtime SwitchSampleGroup and GroupFileUpdateFolder calls found in this ELF are in HandleMessage. This supports serialized ordinary use, but virtual/indirect entry and thread ownership have not been fully proven. The existing cache still lacks a key recheck after obtaining its insertion write lock. Do not add background warming on this evidence.

## Reproduction

Linux x86-64, GCC/binutils and Python 3 are required. The real-library runner needs the separately supplied manifest export.

```sh
gcc -c -o b13_fast_uuid_v4.o b13_fast_uuid_v4.S
gcc -Wl,-z,noexecstack -o /tmp/b13-v4-test test_b13_uuid_v4.c b13_fast_uuid_v4.S
/tmp/b13-v4-test
python3 build_b13_uuid_v4_candidate.py
python3 validate_b13_uuid_v4_candidate.py
python3 audit_real_manifests.py /path/to/px-grp-export
```

To compare v3, supply its assembly source with --version v3 --source /path/to/b13_fast_uuid_v3.S. Recorded outputs are included. Temporary host executable mappings exist solely to run the extracted stock routines; they are not part of the firmware candidate.
